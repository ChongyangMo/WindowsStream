# WindowsStream

## 从源码配置

仓库不包含真实配对口令。构建前，将 `windows/config/client.ini.example` 和 `windows/config/host.ini.example` 分别复制为同目录的 `client.ini` 和 `host.ini`，在两份配置中填写相同的随机配对口令（至少 32 字符），并在 `host.ini` 的 `controller_host` 中填写控制端实际 IPv4 地址。`client.ini` 的内网域名按需填写。

随后运行 `windows/build.cmd`，使用输出的 `build/controller` 与 `build/host` 目录。脚本中的 Visual Studio 工具链路径需与本机安装位置一致。下文的地址和设备数据是原部署记录，新部署需按实际环境配置。

Mac 被控端项目见 [MacStream](https://github.com/ChongyangMo/MacStream)。

基于 MacStream 源码独立开发的 Windows 局域网桌面控制项目。原项目 `C:\Users\Administrator\Desktop\MacStream` 未修改。

## 当前实现

- Windows 控制端、Windows 被控端分开运行。
- TCP 7400，独立 v2 协议和双向口令认证，不依赖互联网。
- B 被控端默认主动连接 A，减少 B 无管理员权限时的入站防火墙问题。
- 优先通过 DXGI 采集主屏，在 GPU 上缩放、转换 NV12，由异步硬件 H.264 编码器编码；控制端使用 D3D11 硬件解码。
- 默认请求 100 fps、48 Mbps；读取真实屏幕刷新率并与硬件编码器协商，不把配置值当作实测帧率。
- 单独发送系统指针形状，支持键鼠控制、文本剪贴板。
- B 通过独立的 TCP 7402 通道拉取经过认证的程序更新，保留 INI，自动备份、替换、重启，并回传诊断。
- 普通权限启动，不安装服务，不修改网卡、防火墙或显示设置。
- 本机 HTTP/HTTPS、SOCKS5 代理，经 B 的独立认证反向连接访问内网，由 B 解析域名。
- 直接连接模式保留了带认证的局域网自动发现。

已完成构建及本机真实桌面检查。B 已回报 Intel Graphics、1920×1200、60Hz；A 为 RTX 3070、2560×1440、100Hz。B 的当前物理显示模式限制真实桌面更新上限为 60Hz。自动升级和旧版引导升级已通过本机真实进程替换检查，B 的本次修复仍需安装后验证。

## 当前连接

网线直连没有 DHCP，B 自动获得 169.254 链路地址（当前 `169.254.155.33`），A 的网卡是手动 192.168 地址。IPv4 只能在同一网段直接通信，B 无权限改地址，所以 A 必须在这块网卡上另有一个 169.254 地址（当前 `169.254.155.34`）。之前该地址是临时添加的，拔插网线或重启后丢失，导致 B 一直找不到 A。

默认由 A 的控制端读取同目录 `client.ini`，`bind_host=auto` 时在全部地址监听 7400/7402/7403，只接受 169.254.0.0/16 网线链路上的对端；B 的被控端读取同目录 `host.ini`，主动连接 A。

两份配置使用本次随机生成的同一口令，未沿用 MacStream 口令。口令由 256 位随机密钥编码为十六进制字符串。

### 网线拔插与地址变化

- A 一次性设置：右键 `build\controller\setup-link.cmd` 以管理员身份运行。它把 `169.254.155.34/16` 写成网线网卡的持久地址，并放行 UDP 7401 自动发现。之后拔插网线、重启都不会丢失。原有 192.168 地址不变。
- 自动发现：B 连续连不上时，只在自己的 169.254 网卡上广播签名请求，并单播询问配置地址和上次成功地址；A 用口令签名应答，B 改用应答来源地址，连接成功后记入 `host.ini` 的 `discovered_host`。A 改用其他 169.254 地址时 B 仍能自动找回；B 自己的地址变化不影响连接。找不到时按 5 秒到 30 秒退避，在配置地址与上次成功地址之间轮换。
- 视频、内网代理、升级三条连接共用发现到的地址；`[proxy] controller_host`、`[updates] host` 显式填写时仍以填写值为准。
- A 的 7400/7402/7403 监听在地址缺失、被移除或端口暂被占用时每 2 秒自动重试，恢复后自动重新监听，不需要重启控制端。相同原因只记录一次日志；本机没有 169.254 地址时单独提示。
- 视频、代理反向连接启用 10 秒空闲、2 秒间隔的 TCP 保活。网线断开后，B 的 64 条空闲代理连接约半分钟内发现失效并重连，不再等 Windows 默认的 2 小时。
- `bind_host` 也可填固定 IPv4 或 `0.0.0.0`，此时不做来源网段限制。

## 手动构建与运行

新规则已取消之前的“不构建”约束；本次完成了必要构建与轻量运行检查。标准构建脚本仍为 `windows\build.cmd`。

1. 需要再次构建时，先从 A 控制端托盘右键菜单选择“退出”，再运行 `windows\build.cmd`，沿用原项目的 Visual Studio 18 Professional 工具链路径。
2. A 使用 `windows\build\controller` 整个文件夹。
3. B 使用 `windows\build\host` 整个文件夹，放到当前用户可写目录后普通双击 `WindowsStreamHost.exe`。
4. A 如果出现防火墙提示，需要允许控制端接收入站连接。B 的系统策略仍可能限制程序运行或出站连接，以实机情况为准。
5. B 默认隐藏到系统托盘，关闭或最小化窗口后继续常驻。右键托盘“退出”才结束；支持当前用户登录自启，不注册系统服务。
6. A 点击窗口右上角关闭按钮后隐藏到托盘，桌面连接和内网代理继续运行。点击托盘图标、“显示窗口”或再次双击 EXE 可恢复窗口；只有托盘右键“退出”才结束程序并恢复原系统代理设置。

构建脚本只在输出配置不存在时复制配置，后续构建保留用户修改。修改口令时，两端实际使用的配置必须同步。

## 当前边界

- 单个主屏，默认按主屏原生分辨率输出（最高 3840×2160），请求 100 fps；最终上限取决于源屏幕刷新率和编码器接受的格式。静止桌面不重复发送整帧来凑帧率。
- 默认 `capture=auto`、`encoder=auto`。优先 GPU 采集和硬件编码；硬件编码运行失败或三秒没有进展时，下次连接改用 GPU 采集、GPU 转换和软件编码，再失败才改用 GDI（上限 30 fps），记录各次失败。
- `capture=dxgi` 要求先成功启用 DXGI；`encoder=hardware` 强制硬件编码，无法启用时报告失败。`encoder=software` 仍优先保留 GPU 采集与转换，`capture=gdi` 才直接启用 GDI。
- 视频采集、GPU 转换、硬件编码选择、异步事件、编码输出、指针及调度分别拆分；最多四帧等待硬件编码，GPU 帧池最大六帧。拥堵时跳过采样，不堆积历史画面，不随意丢弃存在参考关系的 H.264 帧。
- 高精度系统定时器负责采样调度；硬件编码按异步输入/输出事件驱动。
- 未移植变化图块、静止无损发送或自适应码率。控制端保留相应接收能力。
- 不含文件传输、音频、多显示器切换、虚拟显示器或无人值守登录。
- B 物理分辨率不变，控制窗口改变时按比例显示。
- 普通权限不能控制更高权限窗口、UAC 安全桌面和登录界面；检测到安全桌面时断开画面会话，恢复后自动重连。
- Ctrl+Alt+Enter 切换全屏；Alt+F4 将控制端隐藏到托盘；Ctrl+Alt+Delete 由本机系统处理。
- 本版只做认证，视频、输入、剪贴板尚未加密，适用当前受信任局域网。

后续实机检查需要覆盖编译、A 防火墙、B 普通权限运行、首帧色彩、键鼠释放、剪贴板、断线恢复与实际延迟。

## 自动升级

当前 B 的旧版本没有更新接收能力，所以需要最后下载一次 `WindowsStreamHost-RemoteUpdate.zip`，完整解压后运行新版 EXE。旧版仍在运行时，新版会定位旧程序，保留旧目录的 `host.ini`，关闭旧进程后在原位安装并重启；不用手动覆盖正在使用的文件。若旧版没有运行，使用解压目录附带的配置启动新版。

后续只需在 A 更新 `windows/build/host/WindowsStreamHost.exe`。A 控制端运行期间通过 7402 提供程序包，B 默认每 15 秒检查，自动验证和升级，不必再去 B 下载。从托盘主动退出 B 程序后不会继续检查。程序支持当前用户登录自启，不注册系统服务。

更新使用现有配对口令验证请求和清单，并校验 PE 构建时间、程序长度及 SHA-256。只更新程序，不覆盖 INI。旧程序保留在同目录 `.windowsstream-updates`。新版启动后须在 30 秒内连通并验证升级服务，否则回退旧版且不重复安装该失败包。健康检查针对升级通道，画面效果仍需另看视频统计。

B 主动请求升级与上传 `host.log` 增量，升级连接不依赖画面会话。A 只记录经过认证的诊断；更新通道传输未加密，继续限于当前受信任网线网络。B 不需要管理员权限或新增入站规则；A 需要开放对应端口。

INI 可用 `[updates] enabled=0` 关闭升级；A 可配置 `port` 与 `package`，B 可配置 `host`、`port`、`check_seconds`。B 默认升级地址沿用 `controller_host`，端口 7402。

## 经 B 访问内网

A 启动控制端后，本机 `127.0.0.1:1080` 同时接受 HTTP 代理、HTTPS CONNECT 和 SOCKS5 CONNECT。默认还允许 VMware 虚拟机访问，见下文。B 主动连接 A 的 TCP 7403，使用现有配对口令做双向随机挑战认证；代理连接独立于桌面和升级通道。B 不监听入站端口，不改路由，不需要管理员权限。

内网访问直接集成在 A 控制端顶部菜单中。默认在桌面连接及 B 的代理通道就绪后自动开启，普通浏览器跟随系统分流设置，无需 CMD 或专用浏览器。关闭开关、断开或退出会恢复原设置；独立守护在异常退出后恢复。HTTPS 继续由浏览器校验证书。

分流规则位于 `client.ini` 的 `[intranet]`：`networks=10.18.0.0/16`，覆盖 `10.18.0.0` 至 `10.18.255.255`；`domains=sdserver.luxvisions-inno.com`。多个网段或域名用逗号分隔；`*.example.com` 同时匹配根域及子域。缺少该节时使用这些默认规则，保留旧 INI 也会生效。配置变更后关闭再打开内网访问，或重启 A。

系统 PAC 仅将匹配的 IP、域名，以及由 A 解析后落入指定网段的域名送往本机代理并经 B 出口。显式列出的域名不依赖 A 的 DNS，交由 B 解析。其他网站使用 A 原来的直连或手动代理，不进入 B 的转发通道。若一个内网域名在 A 上无法解析，需要将该域名加入 `domains`；不会向 B 查询所有外网域名。原设置使用其他 PAC/WPAD 时暂不叠加，会保留原配置并报告失败，避免悄悄改变外网出口。

自动分流适用于遵循系统 PAC 的浏览器和软件。手动强制指定 HTTP 或 SOCKS5 代理 `127.0.0.1:1080` 会直接使用 B 出口，绕过 PAC 分流规则。这些标准代理入口只转发 TCP。内置 Ping 使用独立的真实 ICMP 请求转发；A 的系统 `ping.exe` 和未配置代理的软件仍使用本机路由。

A 的 `client.ini`：`[proxy] enabled=1`、`local_port=1080`、`tunnel_port=7403`。B 的 `host.ini`：`[proxy] enabled=1`、`tunnel_port=7403`、`connections=16`（1 到 64）。B 的代理控制端地址默认沿用 `controller_host`，可通过 `[proxy] controller_host` 单独指定。历史 INI 缺少该节时也采用这些默认值，B 仅更新 EXE 即可。修改 INI 后重启对应程序；两端隧道端口需一致。

每条反向连接服务一个 TCP 请求，使用有界缓冲区处理背压和半关闭；连接结束后 B 自动补充连接。没有可用通道时 A 最多等待8秒并返回明确失败，不回退为本机直连。退出会中断活动转发并回收线程、套接字。A 的防火墙需允许 TCP 7403；本机代理继续绑定回环地址，虚拟机入口单独绑定 VMware 虚拟网卡。该通道沿用当前受信任网线网络的传输边界，本身未额外加密；HTTPS 内容仍保持端到端 TLS。

### 虚拟机访问

控制端菜单“允许虚拟机访问”默认勾选，`client.ini` 的 `[proxy] allow_virtual_machines=1` 控制此选项；旧配置缺少字段时也默认开启。菜单修改立即生效并保存，关闭时断开虚拟机的现有代理连接，本机代理不受影响。

程序自动识别已启用的 VMware VMnet 私有 IPv4 网卡，仅在这些网卡的地址上监听 `local_port`，仅接受各自同网段的来源。不在物理网卡上开放代理；网卡或地址变化后每两秒检查并恢复。虚拟机入口提供 HTTP、HTTPS CONNECT 和 SOCKS5 TCP 转发，不提供内部 Ping/IP 隧道协议。

首次使用，在宿主机右键 `build/controller/setup-vm-proxy.cmd`，选择“以管理员身份运行”，为当前程序、VMware 网卡和对应虚拟子网添加防火墙规则。网卡地址或代理端口变化后需重新运行；运行时附加 `-Remove` 可移除这些规则。WindowsStream 平时仍以普通权限运行。

虚拟机浏览器使用自动分流配置 `http://192.168.211.1:1080/windowsstream.pac`。该地址只在已允许的 VMware 入口提供，沿用宿主机 `client.ini` 的内网网段与域名规则，并使用请求到达的 VMware 网卡地址作为代理；其他地址直连。它不包含宿主机的配对口令或宿主机原有的代理设置。

运行 `windows/build-vm-browser.cmd` 构建 `WindowsStreamVMSetup.exe`。将 `build/vm-browser` 中的 EXE 和 `client.ini` 放到虚拟机当前用户目录后运行，程序先验证宿主机 PAC 可读，再备份并设置 Windows 当前用户的自动代理脚本，已有的其他手动/脚本代理不会被覆盖。浏览器跟随系统设置，不必逐个填写代理；配置持久保存，不需要在虚拟机常驻额外程序。运行同一个 EXE 并附加 `--restore` 可恢复原设置；修改宿主机地址后更新同目录 INI 并重新运行。

本次实际安装于虚拟机当前用户的本地应用数据目录 `WindowsStreamVMBrowser`，已在虚拟机 Edge 中直接打开 Gitea 首页。宿主机 WindowsStream 仍需保持运行并允许虚拟机访问。

不跟随系统 PAC 的工具仍需显式使用宿主机代理，例如 `curl.exe --proxy http://192.168.211.1:1080 --noproxy "" http://10.18.120.191:3000/`。虚拟机的 `127.0.0.1` 不指向宿主机；显式代理不可用时请求失败，不回退直连。

仅构建控制端时运行 `windows/build-controller.cmd`。它在宿主机使用现有 VS 工具链生成 `build/controller/WindowsStream.next.exe`，将日志写入 `build/controller-build.log`，不替换正在运行的程序，也不重建或升级 B。编译成功后从托盘退出控制端，将旧 EXE 备份后用新 EXE 替换为 `WindowsStream.exe`，再启动。

### 从虚拟机管理宿主机

`windows/tools/host-control` 使用 Windows 自带的 OpenSSH。虚拟机保留私钥，共享目录只存放公钥；连接配置位于 `connection.ini`。宿主机只监听配置中的 VMware 网卡地址和端口，仅允许指定虚拟机通过密钥登录当前本地管理员账户，关闭密码登录及端口转发。组件安装和密钥配置依据 [Microsoft OpenSSH 文档](https://learn.microsoft.com/en-us/windows-server/administration/openssh/openssh_install_firstuse)。

首次在宿主机右键 `setup-host.cmd`，选择“以管理员身份运行”。配置成功后自动写入共享目录的 `host-ready.ini` 和宿主机公钥，服务随宿主机启动。若已有运行中的其他 SSH 配置，脚本不覆盖。IP 变化后更新 `connection.ini` 并在宿主机重新运行。

若 Windows 服务方式启动失败，脚本会记录目录权限、服务信息及前台启动诊断，自动改用 `WindowsStream-HostControl` 系统后台任务运行同一个 OpenSSH 程序。后台任务随宿主机启动并在异常退出后重试，服务方式同时关闭，避免端口冲突；连接地址、来源及密钥限制保持一致。

虚拟机运行 `run-host.ps1 -Command '待执行的 PowerShell 命令'`，客户端会校验宿主机身份。可直接调用宿主机的 `windows/build-controller.cmd --no-pause`，随后运行 `setup-vm-proxy.ps1` 配置代理防火墙。`apply-controller.ps1` 通过一次性桌面任务正常退出旧控制端，备份后替换并启动新版，避免把窗口启动到 SSH 后台会话。

需要撤销远程连接时，在宿主机以管理员身份运行 `disable-host.cmd`，停止服务、关闭自启并移除对应防火墙规则。首次配置日志为 `setup-host.log`；构建和程序更新日志位于 `windows/build`。当前环境的端到端结果应以实际连接、构建和 Gitea 检查为准。

程序记录真实显卡、分辨率、刷新率、编码器名称及每两秒采集/编码/发送统计，静止画面不会用重复帧凑帧率。程序不修改两端系统显示模式。

## 经 B Ping 与 Updater

A 控制端菜单“内网 Ping”可输入 `10.18` 网段 IPv4 地址，每次发送四个请求。B 通过 Windows ICMP 接口真实发送，A 校验响应数据和来源；超时、不可达和通道故障均报告失败。耗时为 B 到目标的 ICMP 往返，不含 A 到 B 的中继耗时；TTL 未提供时显示未知。

Ping 功能通过 A 控制端菜单使用，默认构建不再生成独立命令行工具。B 仍通过已有认证反向连接工作，不需要管理员权限、安装服务或修改网络。

默认构建不再附带或启动 Wintun 网卡组件，原实验 IP 隧道继续停用。此方案不安装驱动、不创建内网路由，不能让 A 自带的 `ping.exe` 自动经 B 转发。

`C:\Users\Administrator\Desktop\netdisk\Updater` 已增加独立 `updater.ini` 网络配置。默认对 `10.18.0.0/16` 和显式内网域名使用 `http://127.0.0.1:1080`；其他目标直连，不依赖系统 PAC 或环境变量。健康检查、列表、上传、删除及发布轮询共用该客户端。先启动 A 控制端，等待 B 连接，再启动带同目录 `updater.ini` 的新版 Updater；服务器地址保持 `http://10.18.32.67:8001`。修改 INI 后重启 Updater。

## 原生分辨率与控制端诊断

默认 `[video] resolution=native`，按主屏真实像素输出，安全上限为 3840×2160。历史 INI 缺少此字段时也默认采用原生策略，因此 B 自动更新 EXE 后即生效，无需覆盖 INI。需要主动缩小时设置 `resolution=limited`，此时沿用 `max_width` 和 `max_height`。

控制端在视频分辨率变化时，优先将窗口客户区适配为 1:1；工作区放不下时等比缩小。用户随后手动调整窗口大小会保留，重连相同分辨率不会反复改尺寸。

标题栏每秒显示输出尺寸、接收与显示提交帧率、协商上限、RTT、采集时间戳至显示提交的估算耗时、码率和编码路径。没有时序样本时显示横线。显示提交不等于物理屏幕扫描完成，跨机时钟用最近16次往返中的最短样本校准。

`client.log` 与 `performance.jsonl` 每两秒记录当前测量窗口的数据，包含 B 的源分辨率/刷新率、采集与编码耗时、实际输出帧率、排队、背压，以及 A 的解码、渲染、排队和显示缩放。结构化日志中的未知值为 null；远端诊断超过6秒标记为过期。日志满4MiB轮转，不记录口令或剪贴板内容。静止桌面实测帧率下降属于没有新画面，不用重复帧凑数。

修正硬件编码输出格式变化后的处理：一次异步输出事件只取一次输出，重新协商后等待下一事件，避免额外 ProcessOutput 调用触发 Intel E_UNEXPECTED。保留三秒停滞检测和 GPU 软件编码回退。

## B 后台常驻

默认开启当前用户登录自启、托盘隐藏、阻止系统自动睡眠和异常退出恢复。升级后的旧 INI 缺少 `[background]` 时采用同样默认值，无需手动覆盖配置。启动项写入当前用户的 Windows Run 注册表项，仅使用普通用户权限，用户登录后生效，不提供登录界面前的系统服务。

关闭或最小化主窗口后继续在托盘运行，托盘提示显示当前连接状态。双击程序或点击托盘可显示窗口；右键菜单提供“显示窗口”“开机启动”“保持唤醒”“退出”。Explorer 重启后重新注册图标；图标的固定或折叠位置由 Windows 管理。

后台常亮保护同时申请系统与显示器持续唤醒，抑制自动息屏、自动睡眠和当前会话屏保，并尝试写入当前用户禁止锁定设置。程序退出或关闭保护后恢复原设置。显式休眠、注销和关机及强制安全策略仍由 Windows 处理，不修改系统电源计划和系统级安全策略。

异常退出由当前用户下的独立守护进程检测，两秒后尝试恢复。每分钟最多五次恢复，超过后等待一分钟再试。守护的程序副本位于 `.windowsstream-runtime/<程序哈希>`，避免锁住主 EXE 影响自动升级。仅传递目标进程和停止事件的必要句柄，并校验原进程路径与创建时间。

主动“退出”、系统注销或升级时停止守护，不会再被拉起。升级助手使用专用退出消息，兼容尚未加入托盘的旧版本；替换、重启、健康检查及回退流程保持不变。

配置项：`[background] autostart=1`、`tray=1`、`start_hidden=1`、`keep_awake=1`、`watchdog=1`。改为0可关闭对应功能，直接改INI后重启生效；托盘中的自启/唤醒开关即时生效并保存。托盘退出不会删除下次登录的启动项，需要取消自启时可先在菜单中关闭。

本机已轻量实测托盘隐藏/显示、关闭不退出、启动项启闭、真实异常终止后恢复、主动退出不再恢复及守护开启后的自动升级。B 的托盘、启动项与唤醒启用结果通过实际诊断日志确认；未为验证而重启 B。

## 常亮与锁屏保护

`keep_awake=1` 现在同时请求 ES_SYSTEM_REQUIRED、ES_DISPLAY_REQUIRED、ES_CONTINUOUS，启动后回读线程请求，每30秒续期；从休眠恢复后重新申请。托盘开关名称为“屏幕常亮”。

通过当前会话 SystemParametersInfo 暂停屏保，不永久写入用户屏保配置。尝试在当前用户下设置 DisableLockWorkstation=1，回读确认，保留原值/原先不存在的状态。权限不足时明确记录错误，不修改系统级策略、不提升权限。

原设置和进程创建时间保存在 `.windowsstream-runtime/awake-state.ini`。正常退出、关闭保护或注销时恢复；异常退出后由守护恢复或交给重启进程接管。升级助手在交接期间持有系统与显示器请求，旧进程保留恢复记录，新进程接管，失败回退时恢复旧状态。

这些措施不能保证拦截 Windows 的全部锁定和主动睡眠路径。当前用户设置即使写入成功，实际生效仍受系统版本、管理策略和 Windows 权限约束；机器强制空闲锁屏策略只读取并记录。开启空闲保活后会按用户配置发送有标记的零位移鼠标活动，并记录实际结果。

已用真实 powercfg /requests 检查显示器和系统两个电源请求，检查屏保/锁定设置及退出恢复，并通过常亮开启时的异常恢复和自动升级检查。没有为测试而实际锁屏或使设备睡眠。

## 无交互的空闲保活

用户启用常亮保护时，默认每秒读取当前登录会话的真实 GetLastInputInfo，连续120秒没有键鼠输入才发送一次零位移鼠标活动（SendInput/MOUSEEVENTF_MOVE，dx=dy=0）。不发送鼠标按下、抬起、滚轮或键盘事件，不选择屏幕坐标，不改变焦点。

本地输入及从控制端注入的真实控制操作均会推迟保活。发送后下一次定时检查确认 Windows 空闲计时是否刷新，并限制两次尝试间隔至少120秒。没有选取所谓“安全点击位置”，因为应用界面随时可能变化，无法保证某个坐标永远没有交互。

按键或鼠标键仍按住时跳过；提交前再次检查最后输入时间，避免与用户刚恢复的操作重叠。锁屏和安全桌面跳过，不尝试解锁。普通权限受到 UIPI 等限制时记录失败，不回退为真实点击。

配置为 `[background] idle_pulse=1`、`idle_seconds=120`；缺失字段沿用这些默认值，因此升级 EXE 后生效，B 无需覆盖配置。托盘关闭“屏幕常亮”时一并停止空闲保活，退出或注销时停止定时器。

已调用生产代码发送真实零位移事件，检查 Windows 空闲计时刷新、光标坐标不变、前台窗口不变、鼠标按钮状态不变；不将配置值当成实际生效结果。
